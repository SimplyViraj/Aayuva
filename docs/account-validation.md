## Integrity and security review

Persistence preserves existing user/session UUIDs. The account migration introduces ONBOARDING defaults without inferred verification or privilege. Static PostgreSQL CHECKs and a partial active-phone index complement service transactions. The follow-up `202610140001_india_e164` migration aligns structural India/E.164 checks with maintained numbering metadata; valid metadata does not prove SMS deliverability. Previously applied migration files remain intact. Production history/initialization remains a separate gate.

Pending and email credentials are independently generated 256-bit capabilities with purpose-separated SHA-256 verifiers. No email proof/hash/provider subject/phone reference is serialized in status DTOs. The pending capability is compared again under the claim lock: cancellation/rotation and concurrent completion cannot create another identity or reuse obsolete authority. Canonical collisions refuse creation; unverified matches never merge accounts. Contacts/profile duplicated in a completed context are cleared, while own-context completion status is available only until its capability expiry.

PostgreSQL transactions, shared database time, sorted advisory rate locks and conditional writes enforce cross-instance budgets and one local transition. Refused phone collisions consume a committed request reservation. Invalid email submissions consume their committed submission budget. Provider delivery success never marks a contact verified; a bound approved check is required. Indeterminate checks retain their reserved failure charge. Unknown phone-send references require the approved validity/deadline wait before restart; unreconciled state grants nothing. Cancelled/expired contexts release their active phone reservation only after local expiry and ten minutes plus the outbound deadline since the last send, using the same configured service. A new request creates a fresh binding and never adopts the old provider reference; tests prove early refusal and later safe release. No automatic sensitive replay or local OTP fallback is implemented.

Twilio/Resend calls use fixed HTTPS hosts, server-only credentials, 10-second deadlines and 64 KiB response limits. Errors are sanitized through the existing global diagnostics/error boundary. SMS code values exist only in the transient provider check call, never storage, hashes, responses or diagnostics. Resend plaintext proof is transient; stored verifiers are removed immediately at consumption/supersession. Email expiry begins at issuance and resend supersession is committed before delivery, so failed delivery never restores an old authorization.

Onboarding capability and ordinary authentication are distinct. `RegistrationModule` is prepared but absent from AppModule; its default primary verifier rejects activation. AUTH_* activation flags remain rejected. The global public inventory contains only the ten reviewed prepared registration IDs; each handler performs its own required proof check. Session authentication now also rejects ONBOARDING accounts when checking a stored session. Completion produces no JWT/refresh credential, privileged assignment or protected navigation.

Mobile pending capability storage is separate from refresh storage and uses native SecureStore. Every restoration queries backend status. Epoch/mount checks suppress obsolete completions; changed account APIs remount form state. Codes/email proofs are transient and cleared before submission; email proof is cleared in both route/form state on use or resend, and route parameters are removed after capture. Read-only status recovery does not replay sensitive work. UI timers display backend resend times; server budgets remain authoritative. Existing accessible notices, labels, scalable text, keyboard/scroll containers and 48-point actions are reused; actual screen-reader/keyboard/lifecycle results are not claimed.

The maintenance service implements only approved registration retention, using indexed time predicates and an hour of headroom for a monitored hourly invocation. It never deletes stable users/sessions. No scheduler/topology/key rotation is silently invented. No age/guardian/demographic collection, account merge/linking, actual credential sign-in, recovery/reset, session issuance or privileged action workflow is introduced. Foundation dependency findings remain unresolved release-remediation gates; no new audit or fix is claimed here.
